# Stage 6 Phase 0 security and architecture review

## Scope

This review covers only the isolated spike in `tooling/crypto_spike`. It does not describe BeChat production behavior and does not establish that BeChat has E2EE.

## Tested Noise configuration

- `Noise_XX_25519_ChaChaPoly_SHA256`
- `Noise_IK_25519_ChaChaPoly_SHA256`
- `snow 0.10.0`, default resolver
- `flutter_rust_bridge 2.13.0`
- Prologue: `BeChat crypto spike v1`
- X25519 static identity keys generated by Snow
- SHA-256 public-key fingerprint, hex encoded

The Rust tests passed for both suites. The Android integration tests exercised the same bridge API on an x86_64 Android 16/API 36 emulator.

## What Noise provides

- `XX` authenticates both static keys by the end of the handshake.
- `IK` lets the initiator encrypt to a known responder static key; the responder authenticates the initiator after processing the first message.
- Completed transport states provide confidentiality and integrity for application messages.
- Modified transport ciphertext is rejected by ChaCha20-Poly1305 authentication.
- Malformed/truncated handshake input is rejected and leaves the session failed.

Noise does not provide application-level trust, authorization, safety-number display, key rotation policy, or protection against a compromised endpoint. Those remain application responsibilities.

## App-enforced identity checks

The spike stores an optional expected remote public key on each session. When the handshake completes, the bridge compares the key returned by Snow's `get_remote_static` with that expected value. A missing or mismatched key fails the session.

`create_session` requires an expected remote key for an `IK` initiator. `XX` sessions can be created without one for first contact, but a production `XX` flow must still obtain user confirmation and pin the resulting key.

Snow returns the authenticated remote static key after the handshake; it does not decide whether that key is trusted. BeChat would need pinning, key-change failure, and out-of-band safety-number verification in the application layer.

## Secure-storage findings

The spike used `flutter_secure_storage 10.3.4` with Android options namespace `bechat_crypto_spike`.

Android implementation observed in 10.3.4:

- The default key cipher is RSA-OAEP with SHA-256/MGF1.
- The RSA private key is generated and kept by the Android Keystore under an app-specific alias.
- The storage cipher is AES-GCM.
- A random AES data key is wrapped by the Keystore RSA key.
- The wrapped AES key and AES-GCM ciphertext are stored in `SharedPreferences` as Base64 strings.
- `read` decrypts the value in the plugin process and returns the plaintext `String` to Dart.
- The test value round-tripped successfully on Android.

### Private-key exposure

The plugin API is string-in/string-out. If a Noise static private key were stored as a value, it would be:

1. held as plaintext in the Android plugin/process during retrieval,
2. sent over the Flutter platform channel,
3. materialized in Dart memory,
4. passed into the Rust bridge as bytes.

That does not satisfy a requirement to keep the long-term private key isolated from Dart. Android Keystore protects the wrapping key and data at rest; it does not make the stored value opaque to the application.

A stricter design would need a native Keystore-backed key provider with an opaque handle, plus a native/Rust integration that uses the key without exposing its bytes to Dart. Rust/Snow still needs a usable static private key for the Noise handshake, so this requires an explicit design and review; it is not demonstrated here.

### Backup, reinstall, and restore

`flutter_secure_storage` documentation warns that Android Auto Backup can back up the encrypted preferences without the Keystore key, causing unwrap failures after restore. The plugin defaults `resetOnError` to true, which can erase recoverable data after an error.

The spike manifest explicitly sets:

```xml
android:allowBackup="false"
```

Production `android/app/src/main/AndroidManifest.xml` does not currently set `android:allowBackup`. That must be resolved before persistent identity keys are added. Disabling backup or excluding the secure-storage preferences is required, and the resulting key-loss/reinstall behavior must be product-defined.

Uninstalling the app removes the Keystore key and stored ciphertext. A restored backup may contain ciphertext but not the device-bound Keystore key. Neither state can silently preserve the same Noise identity. The application needs an explicit identity-loss/re-enrollment path.

## RNG and key persistence

- Static keys are generated with Snow's `Builder::generate_keypair`, which uses the default OS-backed resolver.
- Session ephemerals are generated by Snow for each new handshake. The test confirms two independent sessions produce different first messages.
- The spike does not persist keys. It confirms generation and in-memory session behavior only.
- Long-term key generation, storage, rotation, deletion, and recovery remain unimplemented.

## Zeroization

- The local static private-key buffer in the bridge registry is wrapped in `Zeroizing<Vec<u8>>`.
- Snow's internal handshake and transport state zeroization was not verified.
- The bridge, platform channel, Dart heap, and Android plugin may retain copies of plaintext key material.
- No claim is made that all private-key copies are wiped.

## Failure behavior

- Decryption authentication failure marks the session failed and returns a generic error.
- Handshake authentication/validation failure marks the session failed.
- Operations on failed or closed handles are rejected.
- Error strings do not include keys or ciphertext.
- A syntactically valid but unauthenticated first handshake message may be accepted and answered; authentication failure occurs later. Truncated and oversized input is rejected immediately. Production code needs resource limits and handshake timeouts.

## Build/runtime observations

- FRB 2.13.0 and Flutter 3.35.4 worked with the Cargokit backend.
- Cargokit compiled for armv7, arm64, x86_64, and i686.
- The Android integration test loaded `libbechat_crypto_spike.so` and completed the Rust calls on an x86_64 emulator.
- No physical Android device was connected. Physical-device timing, memory, Keystore, backup, and BLE behavior were not tested.
- Cargokit emitted "system cannot find the path specified" messages during Windows builds, but the APK and runtime tests succeeded. This should be investigated before treating the build as clean.

## Unresolved requirements

- Native, opaque Keystore-backed static-key storage, or an explicit decision to accept Dart/plugin exposure.
- Backup policy and identity recovery after restore/reinstall.
- Long-term key persistence and rotation.
- Safety-number UX and remote-key pin mismatch policy.
- Session rekeying, replay policy, lifetime limits, and resource limits.
- BLE framing and fragmentation limits for Noise messages.
- Local message-database encryption.
- Metadata protection.
- Formal audit of Snow and the Rust FFI surface.
- Physical-device testing and coexistence with BeChat's existing BLE runtime.

## Conclusion

The Rust/FRB/Android bridge is feasible on the current toolchain. Both required Noise suites work through Rust and through the Android bridge, and tamper/failure handling behaves as expected in the spike.

The secure-storage requirement is not fully satisfied: the tested plugin exposes plaintext key material to the app/Dart and needs a stronger native design, plus a backup/reinstall policy. The spike therefore supports a **conditional GO for further development**, not a production E2EE claim.
